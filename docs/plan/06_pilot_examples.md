This is a concrete task for the pilot phase. It produces, for each of the 30
template groups, a viability diagnostic and a small set of worked examples
covering both supported and refuted hypotheses. It runs before any full
benchmark generation and its output is reviewed to recalibrate the provisional
sampling numbers.

Read first: `CLAUDE.md`, `02_dataset_design.md` (leveled-order schema and
gold-label rules), `03_templates.md` (the group roster and registers),
`04_corpus_survey.md` (pilot and distribution-report spec), and `decisions.md`
(locked and provisional decisions). The sampling numbers (T = 100, 45/45/10
verdict balance, min-n) are provisional; do not scale beyond the examples
described here.

## The central requirement: cores must actually exist

A template can only yield a usable hypothesis if its underlying factual core
actually exists in the data. You cannot ask "is the most common ordering
A -> B -> C after Pfizer" unless A, B, and C genuinely co-occur in enough
Pfizer reports to have an observable ordering. Before generating any example,
verify the core exists and clears the group's minimum-n gate.

This matters most for how refuted examples are built:

- A **supported** hypothesis asserts the relation the data actually shows
  (the true majority direction, the true modal ordering, the true first
  event).
- A **refuted** hypothesis takes the SAME existing core and asserts a FALSE
  relation about it (the wrong direction for a pair that is genuinely ordered
  the other way; a wrong ordering of events that do co-occur; a wrong first
  event among candidates that do co-occur).

The events in a refuted hypothesis must still genuinely co-occur. Only the
asserted relation is false. Do NOT build refuted examples from events that
never appear together: a model could then "refute" by noticing the events are
absent rather than by reasoning about their order, which tests the wrong
capability. Refuted means real events, false claim.

## Steps

### Step 1. Build the leveled-order representation
If the leveled-order converter does not already exist, build it from MedTempo
per `02_dataset_design.md` (list of co-exist clusters in temporal sequence per
report). Run the cycle check and report any report whose directional relations
form a cycle (these indicate a conversion error). If the converter already
exists in the repo, use it and note its path.

### Step 2. Core existence and viability
For each template group, enumerate candidate factual cores and keep only those
that actually exist and clear the group's minimum-n gate:

- precedes groups: pairs (A, B) ordered together in at least min-n reports
  (co-exist excluded from the precedes denominator).
- co-occurs groups: pairs (A, B) both present in at least min-n reports.
- sequence groups: triples (A, B, C) that genuinely co-occur in at least
  min-n reports, with an observable ordering.
- first/last groups: triples that co-occur with a determinable earliest or
  latest, ties excluded.

Minimum-n gate (provisional): 20 per cohort for pairwise and co-occurs; 30 per
cohort for sequence and first/last; plus the expected-count guard for the
k-category distribution tests (every cell expects >= 5). A core that does not
clear the gate is not viable and produces no example. Apply the gate through
the shared min-n helper (see `decisions.md`) so creation and later model
evaluation use the same threshold.

### Step 3. Per-template diagnostic
For each group, report:
- number of viable cores;
- the n-distribution across viable cores (min, median, max);
- the fraction of cores that clear the min-n gate vs fall to insufficient;
- for the chi-square-referenced distribution groups (S-V3, S-V4, S-M3, F-V1,
  F-V2, F-M1, F-M2): the fraction where every expected cell count would be
  >= 5 (approximation-safe) vs where the instance must be insufficient;
- a flag for any group with fewer than ~50 viable cores (under-target for
  T = 100, since refuted instances are generated by flipping supported cores).

### Step 4. Worked examples per template
For each group, pick a few viable cores and generate both verdict types from
each:

- **Supported**: assert the relation the data actually shows; gold verdict
  computed from the real counts.
- **Refuted**: take the same existing core and assert a false relation about
  it, per the central requirement above.

For every example, render the four registers (Original, Research, Media,
Clinical) in both question and claim form, and attach:
- the gold verdict (supported / refuted / insufficient);
- the conditioned counts (k, n) the verdict was computed from;
- the test that applies (per `03_templates.md` and the docx reference).

Surface, do not silently drop, any group that cannot produce both a supported
and a refuted example from viable cores. That is itself a finding about the
group's viability.

### Step 5. Validation sample
From the examples, set aside 20-30 cores spanning the families and answer
types, with their raw inputs recorded (the cohort, the per-report leveled
orders involved), so the gold labels can be hand-checked against the source
annotations before the diagnostics are trusted. If code and hand-check
disagree, fix the gold-label code before relying on Step 3's numbers.

## Outputs

Write to `data/pilot/`:
- `template_diagnostics.md` (and optional `.json`) for Step 3.
- `examples.md` or `examples.jsonl` for the Step 4 worked examples.
- `validation_sample.md` for Step 5.

Do not scale beyond these examples. After review, the provisional sampling
numbers in `decisions.md` are recalibrated from the diagnostics, and only then
does full generation begin.
